window ``130000``–``209999`` 下，aux retention 相對無 aux 的 control，

- Primary（U={3200,3400,…,10000}，n=30 seed-wise late-curve averages）：
  **support**（雙尾 paired Student-t 95% CI 下界 > 0）。
- Terminal u10000 30-seed survival： **indeterminate**（CI 含 0）。
- Terminal held teacher diagnostics：兩臂 agreement／KL 皆非空。aux 的
  **agreement 較高**（0.6678817868232727 對 0.1367487758398056，
  差 +0.5311330109834671），aux 的 **teacher→student KL 較低**
  （0.24085557460784912 對 0.8716331720352173，差
  −0.6307775974273682）。「aux 明顯高於 control」不是正確敘述：KL 是
  越低越接近 teacher。這是 secondary，**不得**單獨當 retention 證據，
  也不得覆蓋 primary。

Checkpoint 頂層 ``source`` 區塊記錄的執行環境
----------------------------------------------

本次修訂逐一 ``torch.load`` 了 **70** 個（35 updates × 2 臂）hash 核對
過的本機 U checkpoint 副本，讀出其頂層 ``source`` 區塊。每個區塊都恰好
七個欄位：``commit``／``created_utc``／``device``／``numpy_version``／
``python_version``／``tool``／``torch_version``。70 個之中下列值**完全
一致**：

- ``python_version`` ``3.12.3``
- ``numpy_version`` ``2.5.3``
- ``device`` ``cuda:0``
- ``torch_version`` ``2.11.0+cu128``
- ``commit`` ``bd7443cd7fbbd72fcb6243afc66dc0bf59025c01``（與鎖定 code
  SHA 相同）

``tool`` 依臂不同（aux ``phase3_ranked_ppo_retention_aux``、control
``phase3_ranked_ppo_retention``），與各自 ``run.json`` 的 ``tool`` 相
符。``created_utc`` 是**逐 checkpoint** 的值，兩臂都隨 update 嚴格遞增，
且都是 UTC：aux 從 ``2026-09-21T07:22:53.834757+00:00``（u3200）到
``2026-09-22T22:32:51.200816+00:00``（u10000），control 從
``2026-09-21T02:28:53.379729+00:00`` 到
``2026-09-22T18:11:03.803373+00:00``。70 個逐檔值全文見支援 JSON
``checkpoint_source_provenance.created_utc_by_arm_and_update``。

**這些是 checkpoint 寫檔時的紀錄，不等於啟動環境快照。** bundle 內沒有
任何 argv 或環境 dump，所以這些值說的是「每次存檔時該行程自報的狀態」。
它們只在「整個 run 是單一未中斷行程」的前提下才能當啟動事實的間接證據；
``status.jsonl`` 只有一個 ``started`` 事件、``update`` 連續 1–10000，與該
前提一致，但那仍是推論而非啟動紀錄。

``device`` 這一項比 ``run.json`` 的 ``provenance.device == "cuda"`` 精
確：checkpoint 記到 ``cuda:0``，固定了寫檔時用的 CUDA device ordinal，
但仍然沒有 GPU 型號、沒有可見裝置數量、沒有 driver 版本。
``torch_version`` 的 ``+cu128`` 是 wheel 的 local-version tag，不是已記錄
的 CUDA runtime 版本，本文件不當它是。

**稽核範圍**：每臂打開 **57** 個檔：55 個 ``ppo_*_update_<N>.pt``、1 個

對過的本機副本），理由與上節「逐檔內容 SHA 未計算」相同。

**三個不可混用的量**：

===========================  ==========  ==========
量                           Aux         Control
===========================  ==========  ==========
checkpoint 檔案紀錄數（檔）  55          55
唯一對應 update 直接證據數   55          54
只能確定性重建的 update 數   9945        9946

1. **checkpoint 檔案紀錄數**數的是**檔案**：每臂 55 個
   update-indexed pack，N 精確等於
   ``{0, 10, 25, 50, 100, 200, 400, 600, …, 10000}``，**全部 55 個**都
   帶 ``extra.rollout_seed_window``，且每個 window 都是**連續 8 個**
   seed 的完整列舉（不是端點對）。缺漏數為 0。
2. **唯一對應 update 直接證據數**數的是 **update**：某個 artifact 直接
   落盤了「鎖定排程指派給該 update 本身」的 window。55 個 pack 之中
   **54 個（全部 u≥1）**符合，u0 那個不符合（見下）。aux 另外有被消耗
   掉的 update-1 校準 window，所以 aux 55、control 54。
3. **確定性重建**覆蓋全部 10000 個 update，但重建值是**算出來的，不是
   觀測到的**，不得說成「已核對的落盤紀錄」。扣掉第 2 列後，沒有對應
   直接落盤觀測的 update 是 aux 9945、control 9946（55+9945 =
   54+9946 = 10000）。

**u0 pack 帶的是 update-1 的 window**：
兩臂的 ``ppo_*_update_0.pt`` 都有 ``extra.update == 0``，但其
``extra.rollout_seed_window`` 是 ``130000``–``130007``，也就是
**update 1 的 window**；鎖定公式在 u=0 應給 ``129992``–``129999``。它是
update 1 跑之前寫下的 pre-training snapshot，欄位記的是「即將被消耗的
window」。因此它是一筆落盤的 window 紀錄，但**不是對應紀錄**：既不能讀
成 u0 有 window（u0 不抽 rollout），也**不**單獨算成 update 1 的直接證
據（欄位標著 update 0，沒有說 update 1 實際消耗了什麼）。

**為什麼 aux 比 control 多一個**：
aux 在 update-1 的 on-policy rollout 上校準一次 alpha，且該次**實際消耗**
的 window 被落盤了三處：``report.json`` 的
``alpha_calibration.rollout_seed_window``、每個 aux pack 內同值的
``extra.alpha_calibration``、以及 aux ``recovery.pt`` 的 ``calib_seeds``
與 ``first_update_rollouts[].seed``，三處都是 ``130000``–``130007``。所
以 update 1 對 aux 是直接觀測到的對應 update。control 沒有校準步驟、任何
地方都沒有 ``alpha_calibration``，其 ``recovery.pt`` 也**沒有**
``calib_seeds``／``first_update_rollouts``／``last_update_rollouts``
任一 key，所以 update 1 對 control 不是直接觀測。

**不增加計數的重複紀錄**：
``ppo_*_final.pt``（兩臂各一）packed ``update`` 為 10000、window
``209992``–``209999``、state-dict SHA-256 與 u10000 pack 相同，只是 file
SHA-256 與 ``created_utc`` 不同；aux ``recovery.pt`` 的
``last_update_rollouts[].seed`` 同樣是 ``209992``–``209999``。這些都只是
**重述已被證據涵蓋的 update**，不提高上表第 2 列。

**範圍限定**：
上表的計數**限定**在「checkpoint packs ＋ aux 校準紀錄」這個範圍內。aux
``recovery.pt`` 顯示 recovery 格式會存 calibration seeds 與首／末 update
的 rollout seed，所以未打開的 201 個 aux recovery archive 原則上還可能在
其他 50 的倍數上提供對應觀測（control recovery 沒有這些 key）。因此
「9945／9946」對上述範圍是精確值，對未打開的 aux recovery archive 而言
是**上界**。

全程 window ``130000``–``209999`` 是由
``rollout_seed_window(u) = [130000+(u−1)*8, 130000+u*8−1]`` 在
u=1…10000 推得的，不是某個落盤欄位。逐檔的 (update, window, 來源檔,
來源檔 SHA-256, 來源欄位, 證據類別) 全文見支援 JSON
``rollout_seed_window_provenance.observed_update_to_window_source_list``
與 ``checkpoint_pack_seed_window_inventory``。

Primary estimator
-----------------

鎖定：

1. ``U = {3200, 3400, …, 10000}``，35 點。
2. 對每個 eval seed ``s ∈ {3000,…,3029}``，
   ``d_s = (1/35) * Σ_{u∈U} (elapsed_aux(u,s) − elapsed_control(u,s))``。
3. ``d̄ = mean_s d_s``；n=30 paired Student-t 雙尾 95% CI。
4. 禁止把 35 個 checkpoint 當獨立樣本；禁止刪種子；禁止改 U。

結果（全部由本次修訂從 RO packed ``eval_summary.per_seed`` 重算）：

- n = 30、df = 29
- ``d̄ = +3.20230158730141`` s
- sample SD ``s_d = 4.273837941612275``（分母 n−1）
- t 分位數 ``t_{0.975, 29} = 2.0452296421327043``。方法：以 regularized
  incomplete beta 建的 Student-t CDF，用 ``mpmath.findroot`` 在 **60 位十
  進位工作精度**下求根，得
  ``2.045229642132704298193772221507074957687``（40 位有效位），再**四捨

  稱，已撤回。CI 端點本身是用一般 double 精度算的，所以其末一兩位會隨反

相對 preregistration「完成後必記錄的欄位」的偏離
-------------------------------------------------

Preregistration 的「完成後必記錄的欄位」清單有幾項無法照字面滿足。逐項
說明，全部 **非阻擋**（不影響 primary 的有效性，但必須明說）：

1. **完整 argv、host、Python、CUDA 版本**：argv、host、GPU 型號／數量／
   driver、CUDA runtime／driver 版本 runner 沒寫，事後無法補，標記
   unavailable、不虛構。Python 與 numpy 版本**其實有記錄**，但記在
   checkpoint pack 的 ``source`` 區塊而不是 ``run.json``：70 個 U
   checkpoint 一致為 ``python_version`` ``3.12.3``、``numpy_version``
   ``2.5.3``、``torch_version`` ``2.11.0+cu128``、``device`` ``cuda:0``。
   那是 checkpoint 寫檔紀錄，不是啟動快照，這個限定必須一起帶著。
2. **鎖定的 NAS RO ``INIT_CHECKPOINT`` 絕對路徑 + 啟動時重算 SHA**：
   bundle 有 init file／state-dict SHA-256，沒有路徑。因此「
   ``INIT_CHECKPOINT`` 是那個鎖定絕對路徑」這條 acceptance **無法評定**。
   已核對的是 content identity；launch path 明說未核對，不改寫成通過。
3. **teacher state-dict SHA-256**：runner 只寫 teacher file SHA-256。標記
   unrecorded，不用其他 journal 的 GB10B 值回填。
4. **alpha 校準全文（八 pair、norms、cosine）**：只有聚合平均、cosine、
   ratio 與 alpha 落盤。聚合值逐字記錄；8 組個別 norms 標記 unrecorded。
5. **每 update 的 losses／KL／clip／entropy／EV／optimizer steps／
   rollout survival／frames／censor**：完整存在於兩條 progress jsonl，但
   **刻意不**抄進本文件或支援 JSON（否則要內嵌 20000 列）。改以精確 RO
   路徑、SHA-256、byte 數、列數、``update`` 連續性與完整逐列欄位清單綁
   定，見上方「Artifact roots」與支援 JSON ``progress_jsonl_binding``；該
   處的 ``content_description`` 與 ``per_row_fields`` 已逐名對齊，不多列
   也不少列。
6. **每 update 的 rollout seed window**：**未逐 update 落盤**。兩條
   progress jsonl 都沒有該欄位，所以 aux 9945、control 9946 個 update
   沒有對應的逐 update 紀錄。已改為：由鎖定排程
   ``rollout_seed_window(u) = [130000+(u−1)*8, 130000+u*8−1]`` 確定性重
   建，並明說重建值是算出來的；直接落盤且已核對的，是每臂全部 **55** 個
   update-indexed checkpoint pack 的 ``extra.rollout_seed_window``（其中
   u≥1 的 54 個對應到自己的 update，u0 那個帶的是 update-1 的 window），
   加上 aux 被消耗的 update-1 校準 window ``130000``–``130007``，合計
   唯一對應 update 直接證據 aux **55**、control **54**。檔案紀錄、唯一
   對應 update 證據與確定性重建三者已分開陳述，逐檔來源清單見支援 JSON。
7. **u10000 的 checkpoint kind**：u10000 的 pack 沒有
   ``extra.checkpoint_kind``，任何 pack 也沒有存 ``full_snapshot`` 字串；
   全 run 缺該 key 的 update 精確是 ``{0, 10, 25, 50, 100, 200, 10000}``，
   等於 ``report.json`` 的 snapshot update 集合。已改為明說
   ``full_snapshot`` 是由該欄位缺席推導出的分類、該規則只適用於 U，並在
   支援 JSON 逐 checkpoint 標記來源與記錄全 run 證據。
8. **``recovery_archives`` 實際寫入的 N**：已滿足，且是對 RO 目錄直接列
   舉出 201 個 N，不是從 code 的 stride 推論。

結論
----

1. 本配對在鎖定 commit 上兩臂皆 ``max_updates`` 完成 10000 updates，
   schema v4／seed 11／window 130000／terminal teacher diagnostics／
   dataset／init／teacher hashes 與 preregistration 相符。獨立 audit
   artifact 記的是 ``operational_integrity == pass``；它沒有 accept／
   reject 欄位，本文件也不宣稱有 run 層級的 ACCEPTED 判定。**不宣稱**全
   部 acceptance 字面條件都通過：init 路徑那一條因為沒有紀錄而無法評定。
   argv／host／GPU 型號與數量與 driver／CUDA runtime 與 driver／init 絕
   對路徑的缺失是非阻擋 provenance 限制；Python 3.12.3／numpy 2.5.3／
   torch 2.11.0+cu128／device cuda:0 有記錄，但那是 checkpoint 寫檔紀錄
   而非啟動快照。init 的 content identity 已核對、launch path 未核對，兩
   者不可混為一談。

2. Primary 支持 aux 在 seed-averaged 後段 elapsed 上高於 control
   （+3.20230158730141 s；CI 不含 0）。這是 30 個 eval seed 的曲線
   平均差，不是 35 個獨立 replication。

3. Terminal survival 不支持同一方向（點估計為負、CI 含 0）。不得用
   terminal 否證或改寫 primary，也不得用 primary 宣稱 terminal 優勢。

4. Terminal teacher：aux agreement 0.6678817868232727 **高於** control
   0.1367487758398056；aux teacher→student KL 0.24085557460784912
   **低於** control 0.8716331720352173。兩個方向都表示 aux 較貼近
   teacher，但 agreement 是「較高」、KL 是「較低」，不得合寫成同一句
   「aux 較高」。禁止僅憑 survival 宣稱 retention；也禁止僅憑這組
   teacher 數字宣稱 retention 或 promotion。

5. 一格 aux primary censor（u9200 seed3025）相對 control 零 censor：
   禁止把 support 說成未截尾生存優勢。

6. Frames／optimizer steps 不相等。禁止 equal-frame 重詮釋。

7. **Promote nothing.** experimental checkpoints 不得作 production
   初始化。歷史 post-hoc best（aux u5000、control u5400）禁止作為
   本輪 endpoint。

8. Primary 的科學支持仍然成立（support、CI 下界 > 0），但它被上列第 1、
   3、5、6 點與「未記錄／無法取得的欄位」一節限定：它只是 seed 11／
   window 130000–209999 下、30 個 eval seed 的後段曲線平均 elapsed
   優勢，不是 promotion 授權、不是未截尾生存優勢、不是 equal-compute
   結論，也不是已證實的啟動路徑合規。

明確禁止
--------

禁止 promotion；禁止 self-play／learned Spawner／DAgger／critic-warmup
混入；禁止改 PPO knobs、horizon、eval seeds、dataset、retention
ratio、三條 retention RNG；禁止把歷史 alpha 當本輪 alpha；禁止
resume 本 run 或任何非空目錄；禁止 ``--quick``；禁止把 35 個
checkpoint 當獨立樣本；禁止 post-hoc 選 best update；禁止
survival-only retention 宣稱；禁止 equal-frame 重詮釋本契約；禁止
把本 support 推廣到其他 PPO seed／window；禁止單臂失敗後的配對
推論（本輪未觸發）。下一步若要再複製，必須另立 preregistration。
